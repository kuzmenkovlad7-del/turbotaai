## Вопрос 1: Нет подтверждения email — можно что угодно написать, так и должно?

**Текущая реализация:**  
При регистрации через `/api/auth/register` бэкенд вызывает `admin.auth.admin.updateUserById(userId, { email_confirm: true })` — то есть принудительно подтверждает email сразу при создании аккаунта.

**Что говорить тестировщикам:**  
Email-подтверждение намеренно отключено. После регистрации аккаунт сразу активен. Это продуктовое решение для снижения порога входа.

**Ограничение:**  
Любой email (реальный или несуществующий) проходит регистрацию без проверки. Восстановление пароля будет работать только если указан настоящий email.

**Источник:** `app/api/auth/register/route.ts`

## Вопрос 2: Возможен ли вход на нескольких устройствах?

**Текущая реализация:**  
Да. Supabase Auth выдаёт JWT-токены, которые не привязаны к конкретному устройству. При логине на новом устройстве выдаётся новая пара access/refresh токенов. Старые токены продолжают работать до истечения.

**Что говорить тестировщикам:**  
Один аккаунт может быть залогинен одновременно на нескольких устройствах. Подписка/триал привязаны к аккаунту (`account:{userId}`) и доступны на всех устройствах после входа.

**Ограничение:**  
Принудительного logout других сессий при входе нет.

**Источник:** `apps/mobile/src/services/supabase.ts`, `lib/access/access-control.ts`

## Вопрос 3: Какие типы ошибок возвращает backend?

**Текущая реализация:**  
- `401 Unauthorized` — нет токена или токен недействителен
- `402 payment_required` — исчерпан лимит вопросов, нет подписки
- `400 Bad Request` — неверные параметры запроса
- `403 Forbidden` — нет прав на ресурс
- `404 Not Found` — ресурс не найден
- `409 Conflict` — подписка уже активна (при попытке купить повторно)
- `500 Internal Server Error` — внутренняя ошибка сервера
- `502 Bad Gateway` — ошибка внешнего сервиса (WayForPay недоступен)

**Формат ответа:** `{ ok: false, error: "описание_ошибки" }`

**Специфичные коды:**
- `"payment_required"` — блокировка по исчерпанию trial или отсутствию подписки
- `"invalid_promo"` — неверный промокод
- `"login_required"` — промокод только для авторизованных

**Источник:** `app/api/chat/route.ts`, `app/api/turbotaai-agent/route.ts`, `app/api/billing/`

## Вопрос 4: Какая именно языковая модель используется под капотом?

**Текущая реализация:**  
В n8n workflow прописана модель `gpt-5.1-chat-latest` (OpenAI), `maxTokens: 900`.  
Для прямых STT-запросов: OpenAI Whisper (`whisper-1`).  
Для TTS: OpenAI `gpt-4o-mini-tts`.

**Что говорить тестировщикам:**  
Используется передовая языковая модель OpenAI. Конкретная версия модели является внутренним параметром конфигурации.

**Ограничение:**  
Модель можно изменить в n8n без пересборки приложения.

**Источник:** `docs/private-qa/TurbotaAI Psychologist Agent.json` (не публикуется)

## Вопрос 5: Где крутится системный промпт и какой он именно? Он зашит в код приложения или отдается с бэкенда?

**Текущая реализация:**  
Системный промпт находится **исключительно в n8n workflow** — не в коде мобильного приложения и не в коде Next.js-бэкенда. Изменение промпта возможно только в n8n без пересборки и перевыпуска приложения.

**Что говорить тестировщикам:**  
Системный промпт живёт на стороне сервера (в n8n), в коде приложения его нет. Содержание промпта является конфиденциальным и не публикуется.

**Ограничение:**  
Содержание промпта не раскрывается.

**Источник:** `docs/private-qa/assistant-prompts-private.md`, `app/api/turbotaai-agent/route.ts`

## Вопрос 6: Как ИИ запоминает контекст беседы? Передается ли вся история чата при каждом новом запросе?

**Текущая реализация:**  
n8n использует `memoryBufferWindow` — скользящее окно памяти на **60 последних ходов** (пар пользователь/ассистент). Ключ памяти включает `sessionId`, поэтому каждая сессия (чат/голос/видео) имеет свой контекст. История хранится в памяти n8n, а не передаётся клиентом при каждом запросе.

**Что говорить тестировщикам:**  
ИИ помнит до 60 последних сообщений в рамках одной сессии. При начале новой сессии (новый sessionId) контекст начинается заново.

**Ограничение:**  
При рестарте сервера n8n или очистке памяти контекст теряется. Ключ сессии генерируется на устройстве и сохраняется в SecureStore.

**Источник:** `apps/mobile/src/services/storage.ts`, `docs/private-qa/TurbotaAI Psychologist Agent.json`

## Вопрос 7: Где хранятся сессии? Сколько вопросов вглубь он помнит?

**Текущая реализация:**  
- Ключи сессий хранятся в expo-secure-store на устройстве
- Контекст разговора хранится в памяти n8n (memoryBufferWindow)
- Глубина: **60 ходов** (contextWindowLength = 60)
- History чатов (для UI) сохраняется в Supabase (таблицы `conversations` + `messages`)

**Что говорить тестировщикам:**  
Сессия живёт пока открыт экран (голос/видео) или до следующего открытия чата с тем же sessionId. ИИ помнит до 60 последних реплик.

**Источник:** `apps/mobile/src/services/storage.ts`, n8n workflow

## Вопрос 8: Как реализован перевод голоса в текст и текста в голос?

**STT (голос → текст):**  
- Запись: expo-av (M4A, 16кГц, моно, 128kbps)
- Детекция тишины: -45dB, 4500мс после последней активной речи (порог -35dB)
- API: OpenAI Whisper (`whisper-1`)
- Язык передаётся через заголовок `X-STT-Lang`
- Мусорные/тихие транскрипты фильтруются

**TTS (текст → голос):**  
- API: OpenAI `gpt-4o-mini-tts`
- Голоса: "nova" (женский), "onyx" (мужской)
- Текст разбивается на чанки ≤200 символов по границам предложений
- Следующий чанк prefetch-ится параллельно с воспроизведением текущего

**Источник:** `apps/mobile/src/hooks/useVoiceSession.ts`, `app/api/stt/route.ts`, `app/api/tts/route.ts`, `lib/google-tts.ts`

## Вопрос 9: Есть ли ограничение по токенам на один запрос?

**Текущая реализация:**  
В n8n задан лимит `maxTokens: 900` на ответ ИИ. Максимальный размер входящего текста в чате ограничен 2000 символами (на клиенте). Для голоса/видео максимум записи — 60 секунд.

**Что говорить тестировщикам:**  
Ответ ИИ ограничен ~900 токенами. По системным инструкциям ответы должны быть краткими (2–5 предложений). Для голоса/видео максимум записи — 1 минута.

**Источник:** n8n workflow, `apps/mobile/src/hooks/useVoiceSession.ts`, `apps/mobile/src/screens/ChatScreen.tsx`

## Вопрос 10: Есть ли фильтрация токсичных/опасных ответов?

**Текущая реализация:**  
Системный промпт n8n содержит специальные режимы безопасности (CRISIS_SAFETY_MODE, PANIC_MODE), которые направляют пользователя к профессиональной помощи при признаках кризиса или суицидальных намерений. Отдельного API-уровневого фильтра токсичности нет.

**Что говорить тестировщикам:**  
Базовая фильтрация реализована на уровне системного промпта. При обнаружении кризисных сигналов ИИ переключается в особый режим и перенаправляет на профессиональную помощь.

**Ограничение:**  
Нет внешнего модератора контента (например, OpenAI Moderation API).

**Источник:** `docs/private-qa/assistant-prompts-private.md`

## Вопрос 11: Как устроена анимация аватара в видеочате?

**Текущая реализация:**  
Аватар — два предзаписанных MP4-файла для каждого персонажа: `idle` (ожидание) и `speaking` (говорит). Переключение управляется флагом фазы `"speaking"` в приложении. Реальной lip-sync или генерации видео в реальном времени нет.

Три персонажа:
- `dr-maria` → `avatar1_idle.mp4` / `avatar1_speaking.mp4`
- `dr-sophia` → `avatar2_idle.mp4` / `avatar2_speaking.mp4`
- `dr-alexander` → `avatar3_idle.mp4` / `avatar3_speaking.mp4`

**Что говорить тестировщикам:**  
Анимация — переключение между двумя видеолупами (покой / говорит). Видео генерируется заранее, не в реальном времени.

**Источник:** `apps/mobile/src/screens/NativeVideoCallScreen.tsx`

## Вопрос 12: Видео генерируется сразу или просто двигаем губы на основе аудиофайла?

**Текущая реализация:**  
**Ни то, ни другое в реальном времени.** Используются заранее записанные видеолупы. Видео не генерируется — происходит только переключение между idle и speaking MP4. Реальная lip-sync по аудио отсутствует (класс `VerbalAvatar` в `lib/verbal-avatar.ts` существует в коде, но видеоэкраны используют только MP4, а не canvas-рендеринг).

**Что говорить тестировщикам:**  
Видео — предзаписанные зацикленные анимации. Переключение между "ожидание" и "говорит" происходит синхронно с воспроизведением TTS. Генерации видео в реальном времени нет.

**Источник:** `apps/mobile/src/screens/NativeVideoCallScreen.tsx`

## Вопрос 13: Как приложение понимает, что 5 вопросов кончились? Счётчик привязан к id аккаунта на бэкенде или хранится локально в телефоне?

**Текущая реализация:**  
Счётчик хранится **на сервере** в таблице `access_grants`, поле `trial_questions_left`. При каждом запросе сервер атомарно уменьшает счётчик и возвращает `remainingQuestions` в ответе. Приложение синхронизирует локальное состояние с сервером.

Для гостей — ключ `device_hash` (UUID устройства).  
Для авторизованных — ключ `account:{userId}`.

**Что говорить тестировщикам:**  
Счётчик серверный. Обойти его на клиенте нельзя. При смене устройства (тот же аккаунт) баланс сохраняется.

**Источник:** `lib/access/access-control.ts`, `app/api/turbotaai-agent/route.ts`

## Вопрос 14: Идёт блокировка после 5 вопросов по аккаунту или по IP?

**Текущая реализация:**  
Блокировка **по аккаунту** (account:userId) для авторизованных, **по device_hash** (UUID устройства) для гостей. Блокировки по IP нет.

**Что говорить тестировщикам:**  
Блокировка по аккаунту. При смене устройства без входа в аккаунт — новое устройство получит новые 5 вопросов как гость. После входа — баланс аккаунта.

**Ограничение:**  
Технически возможна обходная атака через регистрацию новых гостевых устройств, но это затруднено тем, что device_hash генерируется один раз и сохраняется в SecureStore.

**Источник:** `lib/access/access-control.ts`

## Вопрос 15: Будет обрабатываться прерывание речи? Сейчас просто диктует ответ. Я задаю вопрос, ноль внимания.

**Текущая реализация:**  
Прерывание речи (barge-in) **не реализовано**. Микрофон открывается только после завершения TTS + пауза 350мс. Пока ИИ говорит, пользователь не может прервать его.

**Что говорить тестировщикам:**  
Прерывание речи — это известное ограничение текущей версии. Ждём завершения ответа ИИ, затем можно задать следующий вопрос.

**Ограничение:**  
Это задача P1/P2 для будущих версий. Требует реализации VAD (Voice Activity Detection) поверх текущего TTS-воспроизведения.

**Источник:** `apps/mobile/src/hooks/useVoiceSession.ts`

## Вопрос 16: Какой максимальный объём текста / лимит надиктовки голосового и видеочата?

**Текущая реализация:**  
- Максимальное время записи: **60 секунд** (MAX_REC_MS = 60000ms)
- Детекция тишины завершает запись раньше: 4500мс тишины после речи
- Максимум вводимого текста в чате: **2000 символов** (ограничение UI)
- Ответ ИИ: **900 токенов** (≈700–750 слов)

**Что говорить тестировщикам:**  
Максимальная запись — 1 минута. Тишина 4.5 секунды автоматически отправляет запрос. Текстовый ввод — до 2000 символов.

**Источник:** `apps/mobile/src/hooks/useVoiceSession.ts`, `apps/mobile/src/screens/ChatScreen.tsx`

## Вопрос 17: На каком этапе происходит самая большая задержка?

**Текущая реализация:**  
Основные источники задержки (от нажатия до ответа):

1. **STT (Whisper)** — 1–3 сек. для аудио 5–10 сек. (зависит от OpenAI latency)
2. **n8n → AI Agent → OpenAI GPT** — 3–8 сек. (основная задержка; зависит от сложности запроса, нагрузки на OpenAI)
3. **TTS первого чанка** — 0.5–2 сек.
4. **Детекция тишины** — 4.5 сек. обязательного ожидания

**Итого типичная задержка конец речи → начало ответа: 8–15 секунд.**

**Что говорить тестировщикам:**  
Большая часть задержки — это AI-обработка в n8n + OpenAI. Это внешний сервис и зависит от их нагрузки. Первый TTS-чанк воспроизводится сразу по готовности, не ожидая полного ответа.

**Источник:** `apps/mobile/src/hooks/useVoiceSession.ts`

## Вопрос 18: Сейчас огромная задержка по обработке ответов, из-за чего она?

**Текущая реализация:**  
Цепочка задержек:
1. Детекция тишины (4500мс обязательно)
2. Загрузка аудио и отправка на Whisper STT
3. Обработка в n8n (webhook latency + AI обработка)
4. OpenAI GPT генерация ответа (до 900 токенов)
5. TTS первого чанка

**Что говорить тестировщикам:**  
Задержка складывается из: детекция тишины (4.5с) + STT (1–3с) + AI (3–8с) + TTS (0.5–2с). Оптимизации: TTS разбит на чанки с prefetch. Уменьшение `SILENCE_AFTER_MS` может снизить субъективную задержку.

**Ограничение:**  
Зависит от внешних сервисов OpenAI. Глобальная задержка OpenAI API в пиковые часы может быть выше.

**Источник:** `apps/mobile/src/hooks/useVoiceSession.ts`

## Вопрос 21: Есть ли разделение prod / staging?

**Текущая реализация:**  
- EAS build profiles: `dev`, `preview`, `production-ios`, `production-android` — разные IAP и store-флаги
- Supabase: единственная prod-база без отдельного staging-проекта (не видно из файлов)

**Что говорить тестировщикам:**  
Staging-окружение существует на уровне мобильных сборок (dev/preview). Отдельной staging Supabase-базы не видно из кода — все среды используют одни таблицы. `/api/dev/reset` доступен только в non-production.

**Источник:** `apps/mobile/eas.json`, `app/api/dev/reset/route.ts`

## Вопрос 22: Какое время жизни access / refresh токена?

**Текущая реализация:**  
Управляется Supabase Auth. По умолчанию Supabase:
- **Access token**: 1 час (3600 сек.)
- **Refresh token**: 60 дней (rotate при каждом использовании)

В мобильном приложении `autoRefreshToken: false` — обновление токенов происходит вручную через хук `useAuth` при фокусировке приложения.

**Что говорить тестировщикам:**  
Access-токен живёт 1 час. Приложение автоматически обновляет его при возврате из фонового режима. Refresh-токен хранится в SecureStore.

**Источник:** `apps/mobile/src/services/supabase.ts`, `apps/mobile/src/hooks/useAuth.ts`

## Вопрос 23: Есть ли rate limit на неправильный ввод пароля при авторизации?

**Текущая реализация:**  
В коде приложения отдельного rate limit нет. Защита обеспечивается встроенными механизмами Supabase Auth: после нескольких неудачных попыток входа Supabase может временно заблокировать попытки с того же IP.

**Что говорить тестировщикам:**  
Явного rate limit в коде приложения нет. Защита от брут-форса обеспечивается на уровне Supabase Auth (серверная сторона). Точные параметры зависят от конфигурации Supabase-проекта.

**Источник:** `app/api/auth/login/route.ts` (нет явного rate limit кода)

## Вопрос 24: Есть ли отдельный код для iOS и Android? Какие функциональные модули имеют отдельную реализацию для iOS и Android?

**Текущая реализация:**  
Большая часть кода общая. Платформо-специфичные различия:

| Функция | iOS | Android |
|---|---|---|
| Запрос разрешений на микрофон | expo-av (автоматически) | expo-av + PermissionsAndroid (двойная проверка) |
| Запрос разрешений на камеру | expo-av | PermissionsAndroid.requestMultiple |
| KeyboardAvoidingView behavior | `"padding"` | `"height"` |
| Promo-код в AccountScreen | Скрыт (Apple Guideline 3.1.1) | Показан |
| Restore Purchases кнопка | Показана (Apple Guideline 3.1.1) | Скрыта |
| Auto-renew cancel/resume | Через API | Через Play Store |
| In-App Purchase | StoreKit + subscriptionOffers | Google Play Billing v5+ (offerToken) |
| Формат записи аудио | M4A (expo-av) | M4A (expo-av) — одинаково |
